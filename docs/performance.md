# Performance measurements

Run `npm run benchmark:win` on Windows after installing the intended build into `.tools/installed`, or pass an executable to `node scripts/benchmark.mjs <path>`. The benchmark launches a separate temporary, key-free profile, waits for the application bridge and native helper, closes its own dashboard through the normal close-to-tray path, then measures the owned process tree across approximately ten seconds of idle time. It verifies the dashboard is hidden, microphone remains off and the process exits cleanly. It does not use the saved Gemini key, record audio or change the clipboard.

Results are written to ignored `artifacts/performance/packaged.json`. CPU is reported both as a percentage of one logical core and of the whole machine. Private commit is the sum of private bytes; the sum of working sets can double-count shared pages. Network measurements count established non-loopback TCP connections at two sample points; an unavailable OS counter is reported as null. Process churn is reported explicitly and can make a short CPU sample unreliable.

The reference workstation target is idle CPU below 1% of one core, microphone off. Key-free benchmark profiles have no provider connection; 0.1.8 can keep a setup-only Google connection ready when a key is configured. Launch timing includes the test connection and application readiness checks. OS caches may already be warm. CDP adds overhead; this is not cold-boot, battery, physical hotkey-latency or clean-machine certification. The earlier `performance-sample.json` is a development observation after microphone use and is not directly comparable with the packaged idle benchmark.

The first successful packaged run used version 0.1.3, build `4a9d663bee58`, on the recorded Windows 11 workstation: 663 ms launch readiness, 11,500 ms observed idle, 0.679% of one core (0.057% of twelve logical cores), six stable processes, 244.8 MiB private commit and 504.3 MiB summed working set. Both network samples were zero, microphone was off and exit was clean. These are individual observations rather than guaranteed resource limits. Re-run against each release before making version-specific claims.

The released 0.1.4 build `9839000c6cfd` was measured again: 832 ms launch readiness, 11,569 ms observed idle, 0.270% of one core (0.023% of twelve logical cores), six stable processes, 257.1 MiB private commit and 424.0 MiB summed working set. Both external TCP samples were zero, microphone was off, dashboard was hidden to tray and exit was clean. See [the complete versioned sample](packaged-performance-0.1.4.json). These results satisfy the reference workstation idle-CPU target for this sample; the caveats above still apply.

The installed 0.1.8 build e4a2306ed5a1 measured 629 ms for the first shortcut and 161 ms for the next to reach Listening, in two real-Google/generated-speech sessions on this workstation. Neither waited for Google setup. Native target capture and microphone opening remain necessary, so this is not a zero-latency guarantee. The separate development sample measured 685/296 ms. Both kept Google ready with the mic off for ten seconds first and ended every captured track after Stop.
